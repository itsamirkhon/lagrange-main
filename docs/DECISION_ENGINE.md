## 1. Задача ядра

Из **подтверждённого** ClientGraph получить **законный и доказуемо лучший** план закупок и поставок одного Rx-препарата при потолках цен, объяснить его и честно измерить эффект.

```
ClientGraph (подтверждённый) ─▶ A. Двойник v2 ─▶ B. Сценарии ─▶ C. Оптимизатор ─▶ План
                                                                    │
                       D. Независимая проверка законности ◀─────────┤
                       E. Объяснение (связывающие ограничения, что-если, «невозможно») ◀─┤
                       F. Измерение (на истине симуляции: прирост, VSS, regret) ◀────────┘
```

**Нерушимые правила:**
1. На вход — только `graph.for_calculation()`. Неподтверждённое не проходит.
2. Все числа считает код. LLM в ядре нет вообще.
3. Каждое законодательное ограничение — из YAML правил, со ссылкой на `rule_id`.
4. Результат воспроизводим: `Snapshot` = хеш входа, сценариев, seed, версий правил, движка и решателя.
5. Нет решения → честное «невозможно» с причиной, а не ослабленные правила.

## 2. A. Двойник v2 (`engine/twin.py`)

Детерминированная функция `twin(graph, sku, scenario) → UnitEconomics` по маршрутам.

**Для каждого маршрута `i` и сценария `s`:**
- **Законная база** `b_is` (для правила 15%) = Kc × курс ЦБ на дату растаможки + пошлина + сборы (+ Pr, если подтверждено) — `UZ-PKM185-LEGAL-BASE`. **Хедж не входит** (`UZ-INV-LEGAL-VS-ECONOMIC-BASE`).
- **Экономическая себестоимость** `c_is` = законная база с учётом хеджа + фрахт по сценарию + `CostItem(layer=acquisition)` маршрута.
- **Затраты ниже линии** — из `CostItem(layer=below_line)` по правилу `allocation` (direct / shared_by_volume / shared_by_revenue). `unallocated` → двойник отказывается считать и называет причину.
- **Потолки (без НДС):**
  - `ChUN_s / 1,12` — опт;
  - `ChChN_s / 1,12 / 1,20` — опт по рознице;
  - контрактная цена продажи, если есть.

  `ChUN_s` — опубликованный, проиндексированный по сценарию (раздел 3). Расхождение опубликованного с формулой п.19 больше 1% → предупреждение.
- **Связывающий потолок** — какой из ограничителей даёт минимум: реестр / 15% / розница / контракт.

**Калибровка (обязательна, это первый экран демо):**
`twin_baseline(graph)` воспроизводит фактическую маржу клиента за последние 12 месяцев по его же продажам и затратам. Расхождение с фактом > 0,5 п.п. → `CalibrationIssue` со списком недостающих данных. Решатель не запускается на некалиброванном двойнике, только с явным флагом «демо-режим, не откалибровано».

## 3. B. Генератор сценариев (`engine/scenarios.py`)

Сценарии строятся **из данных**, а не руками. Каждый генератор с фиксированным `seed`.

| Фактор | Модель | Источник |
|---|---|---|
| Курс USD/EUR/RUB → UZS | блочный бутстрап месячных лог-доходностей за 2020–2026, горизонт 12 мес. | официальный API ЦБ (`fetch_cbu_fx.py`) |
| Потолок: индексация п.20 | рост Rn в сумах ≥3% → индексация 1 января / 1 июля; >5% → сразу + `index_lag_days` (по умолчанию 30) | `UZ-3735-P20-INDEXATION` |
| Потолок: пересмотр вниз | скачок: вероятность `p_cut` за год, глубина из распределения; по умолчанию p = 0,3, глубина U[10%, 37%] (июль 2026: кардио до −37%). Параметры в конфиге, помечены как допущение | `UZ-3735-P22-REVISION` |
| Фрахт | множитель из лог-нормального распределения по виду транспорта | КП / история отгрузок |
| Сбой поставщика или маршрута | Бернулли с `Supplier.reliability` → мощность маршрута = 0 | онтология |
| Спрос | квантили `DemandForecast` (p10 / p50 / p90) | онтология |

- **Выборка:** N = 1 000 сценариев для оценки вне выборки; для оптимизации — сокращение до K = 30–50 с весами (k-medoids по нормированным факторам). Отчёт о расстоянии между полной и сокращённой выборкой.
- **Именованные стресс-сценарии для демо:** «курс +15%», «снижение потолка −37%», «поставщик A недоступен», «фрахт +35%». Они включаются в набор с явной малой вероятностью и показываются отдельно.

## 4. C. Оптимизатор (`engine/optimize.py`)

### 4.1 Этап 1 — обязательный (годовая модель с компенсацией)

Развитие текущего MILP из `lagrange-rx`, переведённое на онтологию.

**Переменные первого этапа** (решаются до раскрытия неопределённости):
- `y_i ∈ {0,1}` — маршрут активирован;
- `x_i ∈ ℤ₊` — заказ в лотах;
- `n_i ∈ ℤ₊` — число отгрузок;
- `h ∈ [0,1]` — доля валютного хеджа (опционально).

**Переменные второго этапа** (по сценарию `s`):
- `e_s ≥ 0` — экстренная докупка авиамаршрутом по повышенной цене;
- `u_s ≥ 0` — недопоставка со штрафом (сервис);
- `q_s` — продажи;
- `R_s` — выручка.

**Выручка — точно и линейно** (общий склад, единая цена, `UZ-INV-UNIFORM-WAREHOUSE-PRICE`):
```
R_s ≤ (ChUN_s / 1,12) · q_s
R_s ≤ (ChChN_s / 1,12 / 1,20) · q_s
R_s ≤ 1,15 · Σ_i b_is · L · x_i  (+ вклад e_s по его базе)     # UZ-PF13-WHOLESALE-MARKUP
q_s + u_s = D_s,   q_s ≤ Σ_i L·x_i·[i доступен в s] + e_s
```
Максимизация выручки делает «min из потолков» точным без бинарных переменных.

**Прибыль сценария:**
`Π_s = R_s − Σ_i c_is·L·x_i − Σ f_i·n_i − Σ F_i·y_i − c^air_s·e_s − penalty·u_s − below_line(q_s) − finance(x, terms)`

**Ограничения первого этапа:**
- партии: `m_i n_i ≤ L x_i ≤ q_i n_i`;
- мощность: `L x_i ≤ U_i y_i`, `n_i ≤ N_i y_i`;
- оборотный капитал: `Σ k_i x_i + Σ f_i n_i + Σ F_i y_i ≤ B` (кредитная линия);
- фильтр допустимости: только `Route.is_eligible`.

**Режимы риска — три разных, явно подписанных в интерфейсе:**

| Режим | Целевая функция | Смысл |
|---|---|---|
| `expected` | max Σ w_s Π_s | максимум в среднем |
| `cvar` (α, λ) | max (1−λ)·Σ w_s Π_s + λ·[η − 1/(1−α)·Σ w_s v_s], v_s ≥ η − Π_s, v_s ≥ 0 | баланс среднего и средней прибыли в худших (1−α) сценариях (Рокафеллар–Урясев) |
| `worst_case` | max z, z ≤ Π_s ∀s | защита от самого плохого из моделируемых сценариев |

Это **двухэтапное стохастическое** программирование (решения до и после раскрытия неопределённости). Мера риска — отдельный выбор. Не смешивать термины.

**Решатель:** HiGHS (`scipy.optimize.milp`); деньги в млн сум, цены в тыс. сум для устойчивости; лимит времени 20 с; на выходе статус, целевое значение, граница и gap. Решение без статуса OPTIMAL помечается как «допустимое, не доказано оптимальное».

### 4.2 Этап 2 — если останется время (помесячная модель)

12 месяцев:
- запасы `I_t` по возрастным корзинам срока годности (FEFO);
- сроки доставки `L_i`;
- помесячный оборотный капитал с отсрочками поставщика и аптек;
- индексация потолка по датам (1 января / 1 июля);
- опционально храповик CIP → будущий Rn (`UZ-INV-CIP-RATCHET`, помечен как допущение).

Добавляется только поверх работающего этапа 1 и с собственными тестами против перебора на крошечных задачах.

## 5. D. Независимая проверка законности (`engine/compliance.py`)

- Читает **только** YAML правил и план + ClientGraph. **Не импортирует** `twin.py` и `optimize.py` (тест на импорты).
- Своя реализация формул: потолки п.19, индексация п.20, правило 15% по законной базе, розничная цепочка ×1,20, НДС.
- Выход — `CheckResult` по каждому правилу и сценарию: `observed`, `limit`, `rule_id`, `passed`.
- **Свойства (property-based, 10 000 случайных графов и сценариев):**
  - любой план оптимизатора проходит проверку;
  - любая мутация правила (15% → 16%, без НДС и т.п.) ловится тестами;
  - двойник и проверка дают одинаковые потолки (сверка двух независимых реализаций).

## 6. E. Объяснение (`engine/explain.py`)

1. **Связывающие ограничения:** остаток ≈ 0 → `Constraint(is_binding=True)` со ссылкой на `rule_id` или на объект онтологии («мощность маршрута ж/д», «кредитный лимит»).
2. **Сравнение с базовой линией** — текущая практика клиента: его фактическое распределение по маршрутам из подтверждённых отгрузок за 12 мес., оценённое **на тех же сценариях**. Waterfall: что дал выбор маршрутов, отгрузок, хедж, экстренная докупка.
3. **«Что если» — только пересчётом.** Изменили параметр (лимит +1 млрд, курс +15%, маршрут недоступен) → решили заново → разница. Двойственные цены MILP не показываются.
4. **«Невозможно, и вот почему»:**
   - если задача недопустима, строится «эластичная» версия: к группам ограничений (спрос, бюджет, мощности, потолки, сервис) добавляются переменные нарушения со штрафом, и минимизируется сумма нарушений;
   - результат — **минимальный набор групп**, которые нужно ослабить, и на сколько: «сервис 98% недостижим: не хватает 1,2 млрд сум кредита или 18 000 упаковок мощности»;
   - **законные ограничения (потолки, 15%) никогда не ослабляются**, они только называются как причина.
5. Человеческий текст объяснения собирается **шаблонами из чисел**, без LLM.

## 7. F. Измерение эффекта (`eval/engine_eval.py`)

Единственный модуль, который читает истину симуляции. Связь с симуляцией — только через формат плана (раздел 8) и `evaluate_plan_on_truth`.

| Метрика | Как считается | Для слайда |
|---|---|---|
| **Калибровка двойника** | маржа двойника по документам L0 vs истина | «двойник воспроизводит 2,5% ± 0,1 п.п.» |
| **Прирост к базовой линии** | `evaluate_plan_on_truth(план) − evaluate_plan_on_truth(база)` на одних и тех же 1 000 сценариях вне выборки | сумы в год, п.п. маржи, CVaR, P(убыток) |
| **VSS** (ценность стохастики) | прибыль стохастического плана − прибыль плана «на среднем сценарии», оба на 1 000 сценариях | «учёт неопределённости даёт +X сум» |
| **EVPI** | идеальное знание будущего − стохастический план | верхняя граница ценности данных |
| **Regret по беспорядку** | план по графу, собранному Ingest на уровне L*k*, оценённый на истине, против плана на истине | «сколько стоит грязь в данных и сколько система спасает», L0–L4 |
| **Законность** | доля планов с 0 нарушений в 10 000 сценариев | должна быть 100% |
| **Оптимальность** | совпадение с полным перебором на 50 мини-задачах; gap | 100% совпадений |
| **Скорость** | время пересчёта после шока | секунды |

Все метрики и пороги **фиксируются до первого прогона** (коммит с хешем). Числа на слайдах — только из `eval/engine_report.json` со snapshot-id.

## 8. Формат плана (контракт с симуляцией)

```jsonc
{
  "plan_id": "...", "sku_id": "<id продукта в ClientGraph>",
  "horizon": "2026-11..2027-10",
  "lines": [{ "route_id": "...", "packs": 60000, "shipments": 4, "months": ["2026-11","2027-02"] }],
  "fx_hedge_share": 0.0,
  "wholesale_price_policy": "max_legal_common_price",
  "risk_mode": "cvar", "alpha": 0.95, "lambda": 0.5,
  "snapshot_id": "..."
}
```

Сопоставление `route_id` и `sku_id` продукта с сущностями истины делает **модуль оценки** по признакам, а не по внутренним ID симуляции. Таблица сопоставления сохраняется в отчёт.

## 11. Definition of done (этап 1)

- [ ] `twin_baseline` на графе из документов L0 воспроизводит маржу 2,5% ± 0,1 п.п. — или выдаёт точный список недостающих данных.
- [ ] Генератор сценариев на реальном курсе ЦБ; индексация п.20 с порогами 3% / 5% (тесты на 2,9 / 3,0 / 5,0 / 5,1%); пересмотр п.22; стресс-сценарии для демо.
- [ ] Оптимизатор этапа 1: три режима риска, статус и gap; совпадение с перебором на 50 мини-задачах.
- [ ] `compliance.py` не импортирует двойник и оптимизатор; 0 нарушений на 10 000 случайных случаях; мутационные тесты.
- [ ] Объяснение: связывающие ограничения со ссылкой на `rule_id`; waterfall против базовой линии; «что если» пересчётом; «невозможно» через эластичную версию без ослабления законных ограничений.
- [ ] `engine_eval`: прирост, VSS, EVPI, законность, оптимальность на L0; regret по L0–L4, когда Ingest соберёт графы.
- [ ] API раздела 9; пересчёт после шока ≤ 5 с.
- [ ] Snapshot у каждого плана; повторный запуск с тем же snapshot даёт тот же план.

## 13. Зависимости от других потоков

- **Ingest:** подтверждённый ClientGraph с маршрутами, отгрузками, растаможкой, продажами и затратами с `allocation`. Пока его нет, ядро разрабатывается на **графе, собранном вручную по документам L0** (fixture в тестах, с пометкой).
- **Симуляция:** реальный курс ЦБ, строки инвойсов по SKU, затраты с привязкой к препарату, `evaluate_plan_on_truth` с форматом плана из раздела 8.
- **Команда:** подтвердить режим риска по умолчанию для демо (предлагается `cvar`, α = 0,95, λ = 0,5) и параметры пересмотра потолка (p = 0,3; −10…−37%).
