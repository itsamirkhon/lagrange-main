# INGEST.md — подключение данных клиента к LAGRANGE Rx

**Статус:** спецификация для разработки, 17.11.2026. **Владелец потока:** один человек или один агент.
**Опирается на:** `docs/ONTOLOGY.md` (особенно разделы 3.1, 6 и 10), `docs/CONTRACT_V2.md`, `docs/SIMULATION.md`.
**Тестовые данные:** репозиторий `langrange-sim`, папки `sim/worlds/L0..L4/documents/`.

---

## 1. Задача

Ingest превращает **кучу документов клиента** в **подтверждённые экземпляры онтологии**, на которых строится двойник.

```
файлы ─▶ 1.Приём ─▶ 2.Разбор ─▶ 3.Классификация ─▶ 4.Извлечение ─▶ 5.Нормализация
      ─▶ 6.Связи ─▶ 7.Проверки качества ─▶ 8.Подтверждение человеком ─▶ ClientGraph (онтология)
```

Это главный «вау» демо: жюри загружает документ, система показывает, что поняла, где сомневается и почему.

**Три правила, которые нельзя нарушать:**
1. **Каждое значение — с доказательством**: документ, страница, цитата, при возможности рамка на изображении.
2. **ИИ предлагает, код проверяет, человек подтверждает.** До подтверждения всё имеет статус `extracted_unconfirmed` и в расчёт не идёт.
3. **Лучше честное «не знаю», чем выдумка.** Если значения нет или оно нечитаемо, создаётся `DataQualityIssue`, а не догадка.

**Ingest и онтология — разные компоненты.**
- Ingest **не определяет и не меняет** онтологию. Он раскладывает данные по уже готовой схеме из `ONTOLOGY.md` (`src/lagrange_rx/ontology/*`, `ClientGraph`).
- Владелец онтологии — продуктовый поток (тот же, кто ведёт двойник). Нужно новое поле или объект → запрос владельцу, а не правка в коде Ingest.
- Пока модели онтологии не готовы, Ingest пишет во временные структуры **с теми же именами и полями** из раздела 3 `ONTOLOGY.md` и переключается, как только они появятся.

**ИИ-провайдер — OpenRouter, везде.**
- Все вызовы моделей идут через **OpenRouter**: извлечение, выбор вариантов, эмбеддинги. Конкретная модель — это строка в конфиге (`config/ai.yaml`), а не код.
- Ключ берётся только из переменной окружения `OPENROUTER_API_KEY`, в репозиторий не коммитится.
- Один клиент `ai/openrouter.py`:
  - ретраи и таймауты;
  - кеш ответов по `(model_id, prompt_hash, input_hash)`;
  - запись `model_id`, версии и задержки в Evidence;
  - лимит расходов на прогон.
- Для демо без сети — Replay-режим из этого же кеша.

**Независимость от симуляции:**
- Ingest не читает `truth/` и `manifest.json` и не опирается на внутренние ID симуляции (`shp_0001`, `lot_0001`, `rte_01`, `SKU_CARDIO_01`). Реальный клиент их не пришлёт.
- Связь строится по признакам реальных документов: названия, номера, даты, количества.
- Манифест и истину читает только модуль оценки.

## 2. Стадии

### 2.1 Приём

- Вход: файлы любого типа — PDF, JPG/PNG, XLSX, CSV, EML, TXT — по одному или папкой/ZIP.
- `SourceDocument.document_id = sha256(bytes)`. Повторная загрузка того же файла распознаётся как дубль байт-в-байт.
- Лимиты: файл ≤ 25 МБ, PDF ≤ 50 страниц. Опасные форматы (исполняемые, макросы) отклоняются.
- Оригинал хранится неизменным. Все дальнейшие артефакты ссылаются на `document_id`.

### 2.2 Разбор (без ИИ)

Цель — получить из файла текст, таблицы и изображения страниц с координатами.

| Тип | Инструмент | Результат |
|---|---|---|
| PDF с текстовым слоем | `pdfplumber` / `pypdf` | текст по страницам со словами и bbox, таблицы |
| PDF-скан, JPG, PNG | `tesseract` (языки `rus+uzb+uzb_cyrl+eng`) + предобработка OpenCV (выравнивание, контраст) | текст со словами, bbox и уверенностью OCR |
| XLSX | `openpyxl` (`data_only=True`) | листы → таблицы. Объединённые ячейки раскрываются, строка заголовка ищется автоматически (не всегда первая) |
| CSV | автоопределение кодировки (`cp1251` / `utf-8`) и разделителя (`;` / `,`) | таблица |
| EML | `email` stdlib | заголовки, тело, вложения как отдельные SourceDocument |

Обязательно:
- **Удалять водяной знак** «УЧЕБНЫЙ ОБРАЗЕЦ / SYNTHETIC» до извлечения. В PDF симуляции `pdftotext` разбивает его на буквы, и они вклиниваются в текст.
- Для каждой страницы сохранять PNG-рендер: он нужен для DecisionScorer и для подсветки доказательства в интерфейсе.

### 2.3 Классификация

DecisionScorer (ONTOLOGY.md, раздел 10), вопросы Q0: `ALL.doc_class`, `ALL.language`, `ALL.about_focus_sku`, `ALL.readability`, `ALL.is_photo_or_scan`, `ALL.has_handwritten_edits`, `ALL.stamp_over_numbers`.

- Документы с `irrelevant` отправляются в отдельную корзину. Вход в расчёт им закрыт, но человек может вернуть.
- При `readability ≤ 1` создаётся `DataQualityIssue(unreadable)` и ставится вопрос человеку.

### 2.4 Извлечение (генеративная модель)

Интерфейс `Extractor`. Реализации:
- `OpenRouterExtractor` — генеративная модель через OpenRouter со структурным выводом (JSON Schema). Модель выбирается в `config/ai.yaml`: семейство Gemini или Claude, с поддержкой изображений для сканов. Выбор фиксируется по результатам оценки (раздел 5).
- `ReplayExtractor` — для демо без сети.

- **Табличные документы (XLSX, CSV) — сначала без ИИ.** Детерминированное сопоставление колонок по словарю синонимов (раздел 3.3). ИИ подключается, только если колонка не опознана: он выбирает соответствие из списка полей онтологии через DecisionScorer.
- **Текстовые документы (PDF, OCR) — ИИ.** На вход подаётся текст страницы с номерами строк (и изображение для сканов), на выход — JSON по схеме класса документа (раздел 3.1).
- **Обязательное поле `evidence` у каждого значения:** страница + точная цитата. После ответа модели **код проверяет**, что цитата действительно есть в тексте страницы (нечёткое совпадение ≥ 0,9). Нет совпадения → значение отбрасывается как галлюцинация, создаётся `DataQualityIssue`.
- Модель возвращает значение **как написано** (`"7,13"`, `"74,33 млн"`, `"03.08.2026"`). Нормализует код, а не модель.
- Температура 0, версия модели фиксируется и записывается в Evidence.

### 2.5 Нормализация (только код, библиотека `ingest/normalize.py`)

| Что | Правила | Если неоднозначно |
|---|---|---|
| Числа | `1 250 000,00`, `1.250.000`, `1,25 млн`, `1250т`, `74,33 млн` → float; различать десятичный и тысячный разделитель по контексту колонки | `DataQualityIssue(arithmetic/unit)` |
| Даты | `03.08.2026`, `2026-08-03`, `06/02/2026`, «апр. 26», месяц словами на ru/uz | Формат `xx/yy/zzzz` неоднозначен → смотреть остальные даты в том же документе; не определилось → вопрос человеку |
| Валюта | символы и коды (`$`, `USD`, `долл.`, `so'm`, `сум`, `€`) | Валюты нет → `currency_ambiguous`, подсказка из контракта или КП того же контрагента |
| НДС | «с НДС / без НДС / QQS bilan / QQSsiz / incl. VAT» | `vat_ambiguous` |
| Единицы | упаковка / блистер / коробка ×N; коэффициенты из Product.pack_size | `unit_ambiguous` |
| Названия | транслитерация узб. латиница ↔ кириллица (`Andijon viloyati` ↔ `Андижон вилояти`), нормализация пробелов, регистра, «мг/mg», «№30/N30» | — |
| Регионы | словарь 14 регионов РУз во всех написаниях | — |
| Курс | только официальный курс ЦБ на нужную дату (API ЦБ, см. `fetch_cbu_fx.py`) | — |

Каждое преобразование логируется: исходная строка → результат → правило. Это нужно для аудита и для оценки.

### 2.6 Связи (entity resolution)

1. **Блокировка (код):** кандидаты по признакам — номер партии, номер инвойса или контракта, контрагент, дата ±7 дней, количество ±5%, нормализованное название.
2. **Оценка (код):** балл сходства по признакам.
3. **Выбор (DecisionScorer, вопросы Q2):** только если у кода не единственный уверенный кандидат. Варианты — до 10 кандидатов + `none_of_these`.
4. Каждая связь хранит уверенность и обоснование: какие признаки совпали.

**Эмбеддинги — опционально и только с доказанным выигрышем.**
- **Базовый вариант (обязателен, без ИИ):** транслитерация узб. латиница ↔ кириллица + нормализация + символьные n-граммы (TF-IDF по 3-граммам). Детерминированно, работает без сети.
- **Эмбеддинги (опционально):** мультиязычная модель эмбеддингов через OpenRouter, имя модели в `config/ai.yaml`. Это **ещё один признак** сходства на этапе блокировки и оценки, не решение.
- **Где используются:**
  - сопоставление названий препаратов, контрагентов и регионов («Kardiozan 10mg N30» ↔ «Кардиозан 10 мг №30», «Andijon viloyati» ↔ «Андижанская обл.»);
  - подбор кандидатов для неопознанных заголовков колонок (3.3);
  - поиск почти-дублей документов (повторный скан того же инвойса).
- **Где запрещены:** числа, суммы, даты, валюты, единицы. Эмбеддинги плохо различают 7,13 и 7,31 или 5 000 и 10 000. Всё денежное — только код и цитата.
- **Решение оставить их** принимается на симуляции: recall и precision связей и сопоставления колонок с эмбеддингами против базового варианта на L1–L4. Оставляем, только если выигрыш есть, и показываем его цифрой. Отдельно проверяется качество на узбекском (латиница и кириллица).
- Векторы кешируются по `(model_id, text_hash)`. Без сети работает базовый вариант.

Связи, которые нужны двойнику:
- накладная ↔ отгрузка;
- инвойс ↔ контракт;
- партия ↔ отгрузка;
- КП перевозчика ↔ маршрут;
- регион в отчёте ↔ регион в 1С;
- «Kardiozan 10 мг №30» ↔ Product.

### 2.7 Проверки качества (в основном код)

Детерминированные правила по графу. Названия совпадают с операторами порчи симуляции, чтобы оценку можно было считать автоматически.

| Проверка | Как | Оператор симуляции |
|---|---|---|
| Противоречие КП ↔ контракт (MOQ, цена, условия) | сравнение полей связанных объектов | X1 |
| Несколько версий контракта | одинаковый номер или контрагент, разные даты или цены → DecisionScorer `C.is_latest_version` | X2 |
| Дубль документа | хеш, затем совпадение ключевых полей | D1x |
| Валюта не указана / не та | значение вне диапазона рынка для валюты; сравнение с контрактом | C1, C2 |
| Курс не на ту дату | пересчёт по курсу ЦБ на дату растаможки ≠ значение в документе | C3 |
| НДС не указан или перепутан | DecisionScorer + сверка с потолком реестра (с НДС или без) | V1 |
| Единицы | количество ×10 / ÷10 относительно связанных документов | U1 |
| Арифметика | итог ≠ сумма строк; закрытие ≠ открытие + приход − расход | A1 |
| Пропуск периода | дыра в помесячном ряду; сверка 1С ↔ региональные отчёты | M1 |
| Устаревание | дата документа или срок действия КП и выписки реестра vs дата расчёта | S1 |
| Нечитаемое, печать, рукопись | DecisionScorer Q0 + уверенность OCR | R1–R4 |
| Мусор | DecisionScorer `irrelevant` | J1 |

**Сверка целого:** после загрузки всех документов Ingest пробует собрать P&L фокус-SKU (продажи, себестоимость, затраты). Если он не сходится или чего-то не хватает, Ingest говорит, **какого документа не хватает** («нет данных о затратах на дистрибуцию за май–июнь 2026»). Это переход к честному «невозможно, и вот почему».

### 2.8 Подтверждение человеком

API и интерфейс:
- **очередь вопросов**, отсортированная по влиянию на деньги, а не по порядку документов;
- **карточка вопроса:** значение, варианты с вероятностями, подсвеченная цитата на изображении страницы, связанные документы;
- **действия:** «верно», «исправить» (новое значение сохраняется рядом со старым), «не относится», «нужен другой документ»;
- **массовые действия:** «принять все высокоуверенные НЕ-денежные значения».

**Жёсткое правило (ONTOLOGY.md, 10.5):** валюта, НДС, единицы, цена, версия контракта на уровнях L2+ — только ручное подтверждение.

## 3. Схемы

### 3.1 Схемы извлечения по классам (Extractor → JSON)

У каждого поля структура `{ "raw": "...", "evidence": { "page": n, "quote": "..." } }`. Нормализованное значение добавляет код.

- **supplier_quote:** supplier_name, quote_number, issue_date, valid_until, product_name, unit_price, currency, incoterms, moq, lead_time, shelf_life, payment_terms, vat_note
- **carrier_quote:** carrier_name, route_description, mode, price_per_shipment, price_per_pack, currency, transit_days, moq, valid_until
- **contract:** contract_number, version_or_amendment, supplier_name, sign_date, valid_until, unit_price, currency, incoterms, moq, payment_terms
- **invoice:** invoice_number, date, supplier, contract_ref, lines[{product, qty, unit, price, lot, expiry}], totals
- **customs:** entry_ref, date, customs_post, cip_value, currency, fx_rate_used, duty, fees, vat
- **waybill:** number, date, product, lot, qty, unit, from, to
- **memo / email:** свободные факты → список `{field_guess, raw, evidence}` только как **подсказки**, в онтологию напрямую не идут
- **registry_extract:** product, registration_number, rn, b, bx, chun, chchn, date

### 3.2 Результат Ingest

```jsonc
{
  "batch_id": "...",
  "documents": [{ "document_id": "...", "doc_class": "...", "class_confidence": 0.97, "status": "parsed|needs_review|irrelevant|unreadable" }],
  "proposed_instances": [{ "type": "Quote", "id": "...", "fields": {...}, "status": "extracted_unconfirmed", "evidence": [...] }],
  "links": [{ "from": "...", "to": "...", "relation": "...", "confidence": 0.82, "features": ["lot_number", "date±2d"] }],
  "issues": [{ "issue_type": "...", "severity": "...", "affected": [...], "evidence": [...] }],
  "review_queue": [{ "question_id": "...", "money_impact_uzs": 0.0, "options": [...] }],
  "coverage": { "missing_for_twin": ["distribution costs 2026-05..06"] }
}
```

### 3.3 Словарь колонок (для табличных документов)

`ingest/column_synonyms.yaml`: поле онтологии → варианты заголовков на ru / uz-latn / uz-cyrl / en. Например:

```yaml
SalesRecord.qty_packs: ["Количество", "Кол-во", "Sotuv (up.)", "Сотув (уп.)", "qty", "Qty, packs"]
```

Словарь пополняется по ходу работы. Неопознанная колонка → DecisionScorer выбирает из полей онтологии + `ignore`.

## 5. Оценка на симуляции (модуль `eval/ingest_eval.py`)

Модуль оценки — единственный, кто читает `truth/` и `manifest.json`. Метрики считаются по каждому миру L0–L4 и по каждому типу документа:

1. **Классификация** — точность `doc_class`.
2. **Извлечение** — точность по полям после нормализации (число ±0,5%, дата точно, валюта точно).
3. **Доказательства** — доля значений с проверенной цитатой; галлюцинации (значение без цитаты в тексте) — целевой ноль.
4. **Обнаружение порч** — precision и recall по каждому оператору манифеста.
5. **Честность** — для порч `recoverable: false` система должна вернуть issue или вопрос, а не значение. Выдуманное значение — грубая ошибка.
6. **Связи** — precision и recall связей против истины.
7. **Нагрузка на человека** — число вопросов на подтверждение. С **симулированным человеком**, который отвечает по истине, — итоговая точность после подтверждения.
8. **Полнота для двойника** — собирается ли P&L и насколько маржа по документам отличается от истинной (цель на L0 — 2,5% ± 0,1 п.п.).
9. **Время и стоимость** на документ.

Выход — `eval/report_ingest_L{k}.json` и сводная таблица для слайда.

Важно: в симуляции сейчас мало порч на оператор (часто по одной на уровень). Пока это не исправлено, метрики показывать с числом случаев рядом («3 из 3»), а не процентами.

## 6. Демо-сценарий Ingest (2 минуты)

1. Жюри перетаскивает папку мира **L3** (около 26 файлов).
2. Экран «Документы»: классы с уверенностью, 1–2 файла помечены как нечитаемые или мусор.
3. Экран «Что мы поняли»: КП, контракты, отгрузки — каждое значение кликается и показывает подсвеченную цитату на странице.
4. Экран «Проблемы»: противоречие MOQ в КП и контракте, две версии контракта, НДС не указан, дубль накладной, пропуск мая.
5. Очередь подтверждений: 5–8 вопросов, отсортированных по деньгам; человек кликает ответы.
6. Кнопка «Собрать двойник»: маржа 2,5% воспроизведена, или «не хватает документа X».
7. Ползунок L0 → L4: та же компания, больше беспорядка — растёт число вопросов, а точность после подтверждения держится. Это главный слайд с метриками.

## 10. Что нужно от других потоков

- **Симуляция:** убрать внутренние ID из документов, добавить документы на все отгрузки и КП, больше порч на оператор (см. ревью). Пока этого нет, Ingest всё равно не должен полагаться на ID.
- **Продукт:** модели онтологии (`ontology/*`) и `ClientGraph`. До их появления Ingest пишет в схему из `ONTOLOGY.md` раздел 3 через временные Pydantic-модели с теми же именами.
- **Команда:** ключ OpenRouter (`OPENROUTER_API_KEY`) и лимит расходов. До старта потока проверить на OpenRouter три вещи:
  1. доступна ли **Gemini Decision 1** (`google/gemini-decision-1`). Это не обычная чат-модель, у неё отдельный Decisions API, и через OpenRouter она может быть недоступна. План Б — в `ONTOLOGY.md`, 10.2;
  2. какая генеративная модель с изображениями и JSON Schema будет `Extractor`;
  3. есть ли нужная модель эмбеддингов.
